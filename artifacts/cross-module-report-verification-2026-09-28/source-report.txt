A01 · TCP 与 AI SSE 逐个网络块解码 UTF-8

优先级： 高。证据性质： 静态协议缺陷。

源码位置（固定在上述提交）：

lib/src/services/friend_realtime/friend_realtime_connection_io.dart — connect / _onChunk

lib/src/api/ai_assistant_api.dart — stream

已确认代码事实： TCP 的 onData 调用 _onChunk(utf8.decode(data))；AI 的成功 SSE 路径调用 parser.feed(utf8.decode(chunk), ...)。两处都在字节流分块边界重新创建单次解码过程。

触发条件： 响应包含未转义的中文、表情等多字节字符，而且接收块恰好从字符中间分开。不是每次网络回调都会触发；服务端只发送 ASCII 转义字符时，这个条件不成立。

可能影响与边界： 完整数据原本合法，独立解码其中一个不完整块仍可抛出 FormatException。TCP 字符串按换行缓存发生在解码之后，不能修补这一问题；AI 会进入服务不可用错误路径。不能据此宣称腾讯 IM 消息传输本身已坏：这里是应用自建 TCP 与 AI HTTP 流。

建议修改方向： 对整条字节流使用有状态 UTF-8 decoder，再做换行或 SSE 帧解析。不要改为 allowMalformed 来隐藏问题；还应限定单帧缓冲大小、明确解码错误后的断连/重试策略。

待执行验收： 构造包含中文和 emoji 的业务 JSON、SSE 帧，遍历所有字节切分点，再测试多帧合并、半个换行和最后一帧结束。应完整还原事件，无丢字、重复或误报服务不可用。

A02 · 用户主动取消请求也被算成 API 节点故障

优先级： 高。证据性质： 静态分类缺陷。

源码位置（固定在上述提交）：

lib/src/api/api_client.dart — _isNodeTransportFailure / onError

lib/src/services/api_node_service.dart — noteRequestFailure / _failoverAfterFailures

已确认代码事实： _isNodeTransportFailure 在 error.response == null 时直接返回 true，没有先排除 DioErrorType.cancel；节点服务累计三次失败后测速、切换节点并触发业务 TCP 重连。

触发条件： 取消的请求经过公共 Dio 的 onError，且失败计数在达到阈值前没有被成功响应清零。不能把任意三个点击取消都断言为必然切线。

可能影响与边界： 退出页面、取消上传或取消流式请求可能被当作网络故障，触发无必要的探测与切线。属于连接稳定性问题，不是直接证明 UI 掉帧。

建议修改方向： 先分类本地主动取消、账号/页面过期取消，再计数真实传输错误。请求携带节点身份与切线代次，旧节点晚到结果不能污染新节点健康状态。

待执行验收： 连续制造三个经过公共拦截器的取消错误：失败计数不得增加，不得测速或切节点；另外验证真实超时仍按策略累计。

A03 · 测速把 502/503/504 也标记为正常节点

优先级： 高。证据性质： 静态健康判定不一致。

源码位置（固定在上述提交）：

lib/src/services/api_node_service.dart — probeNode / pickFastestNormal

lib/src/api/api_client.dart — _isNodeTransportFailure

已确认代码事实： probeNode 的 validateStatus 接受所有状态，收到响应直接标记 normal；但公共 API 将 502/503/504 判定为节点传输故障。

触发条件： 某节点可以快速返回网关错误，另一节点业务响应较慢。

可能影响与边界： 自动选择可能倾向快速失败的节点。当前测速实际上测的是可达性，选择逻辑却把它当成可用性。

建议修改方向： 分开记录 reachability、serviceHealth、latency；健康探针检查明确的状态和轻量响应结构。保留按业务约定处理 401/403 的空间，不把任意有响应都叫正常。合并同时进行的 probeAll 任务。

待执行验收： 模拟一个节点 20ms 返回 503，另一个 200ms 返回符合契约的健康响应。失败节点不得成为 healthy 候选；测速并发时必须等待同一个结果。

A04 · 业务 TCP 认证失败后 force 重连被提前拦截

优先级： 高。证据性质： 静态恢复路径缺陷及超时风险。

源码位置（固定在上述提交）：

lib/src/services/friend_realtime_service.dart — ensureConnected / _connect / _startPing / _handleLine / stop

lib/src/services/friend_realtime/friend_realtime_connection_io.dart — connect / send / close

已确认代码事实： ensureConnected 先检查 _authFailed 并 return，之后才有 force 分支将 _authFailed=false。因此这个重置分支在认证失败时不可达。stop 会重置该标志，不能声称只有杀进程才可恢复。另有 TCP connect 超时和 last_seen 请求超时，但未见独立认证应答截止时间或 pong 存活判断。

触发条件： 发生 auth_fail 后业务端取得新的有效凭证并尝试 force 重连；或者 socket 已连接但认证应答一直不来，或连接半断而本地对象仍存在。

可能影响与边界： 自建 TCP 的重连/就绪状态可能长期停在错误状态。具体调用链是否已有 stop/start 补偿需要结合故障日志核对。

建议修改方向： 按凭证代次区分终止性认证失败与可恢复失败，只在新凭证确认有效后重新开启连接流程。不要对无效账号盲目无限重试。增加认证应答与心跳存活阶段的截止时间及当前连接代次校验。

待执行验收： auth_fail -> 有效新凭证 -> 恢复，无需退出进程；无效凭证不得反复认证。另测连接成功但不发 auth_ok、吞掉所有 pong、前后台切换。

A05 · 回前台可能重复业务验证和两次 SDK login 调用

优先级： 中高。证据性质： 确定调用路径；成本待测。

源码位置（固定在上述提交）：

lib/src/pages/app.dart — _scheduleResumeCheck / _checkIfConnected

lib/src/services/login_coordinator.dart — recoverOnForeground

lib/src/session/session_manager.dart — restore / _restoreInternal / _refreshCredentialInternal

lib/src/session/im_client.dart — connect

已确认代码事实： 前台恢复进入 SessionManager.restore；无在途任务时创建恢复流程，即使此前已 ready。命中缓存凭证时调用一次 _im.connect，随后刷新凭证，满足 ready 条件时再调用一次 _im.connect。ImClient.connect 直接调用 SDK login。

触发条件： 回前台满足 App 的恢复节流条件，缓存凭证路径成功，并且刷新凭证成功。

可能影响与边界： 会反复产生本地凭证读写、HTTP 请求和 SDK 登录调用。SDK 可能内部快速处理同账号登录，所以不能说每次必然建立两次完整网络连接，也不能给出未测耗时。

建议修改方向： 把进程冷恢复、普通短暂 inactive/resumed、断线恢复、凭证到期分开。保留必须的业务鉴权，在线且凭证新鲜时不要重走完整 SDK 登录；刷新可用凭证与重建连接分别处理。

待执行验收： 有效在线会话连续前后台切换，记录 fetchMe、取签名、SDK login、监听绑定次数。正常短切换不得无条件重走整套登录；过期和踢下线场景仍按安全逻辑退出或恢复。

A06 · 重连入口没有把自己登记为在途操作

优先级： 高。证据性质： 静态并发缺口。

源码位置（固定在上述提交）：

lib/src/session/session_manager.dart — _reconnect / scheduleReconnect / _establish

lib/src/session/im_client.dart — connect

已确认代码事实： _reconnect 会检查 _activeOperation != null，但自身直接 await _establish，没有设置 _activeOperation 或另一个重连 in-flight。重试定时器触发前会被清空。

触发条件： 一次 _establish 尚未完成，新的断线事件又安排重试；下一次定时器到达时 _activeOperation 仍为 null。

可能影响与边界： 可能有两个同代次认证/SDK 登录流程交错，造成状态覆盖和重复工作。现有账号 generation 不能区分同账号同代次的两个竞争尝试。

建议修改方向： 让恢复、重新登录、重连共享明确的 single-flight 所有者，或使用统一连接协调器。登记任务、按 identical 释放，旧尝试不再提交状态。不要仅加入固定延迟。

待执行验收： 将取签名或 SDK login 保持 pending，连续触发断线和多个重试定时器。任何时刻有效登录尝试数量应为 1；前一次结束后才能启动下一次。

A07 · 好友/群校准等待 15 秒后绕过聊天让路

优先级： 中高。证据性质： 静态调度行为确定。

源码位置（固定在上述提交）：

lib/src/services/im_sdk_relationship_reconcile_service.dart — _waitUntilRunnable / _request / _productionCanRun / _loadGroups

lib/src/services/im_sdk_relationship_perf.dart — uiIdleTimeout

已确认代码事实： _productionCanRun 在有活动聊天时返回 false；_waitUntilRunnable 最多轮询 15 秒，超时后自然返回，_request 随后继续执行校准。

触发条件： 用户进入聊天并持续使用超过等待期限；任务在此前因聊天活动被延后。

可能影响与边界： 所谓空闲任务可能在聊天进行中启动。群路径会获取已加入群列表，好友路径根据自建关系配置进入联系人协议同步。实际 CPU/数据库影响由账号规模和同步实现决定。

建议修改方向： 等待结果应区分 runnable、deferred、cancelled；未空闲时延后而不是默认放行。必须及时执行的正确性同步应分块、有预算，并在批次之间再次检查交互和账号。

待执行验收： 持续模拟活动聊天超过 15 秒：可选全量校准不得偷偷启动。退出聊天后允许恢复；实时必要事件仍可处理。

A08 · 关系校准的旧异步任务能修改新会话的阶段标记

优先级： 高。证据性质： 静态代次隔离缺口。

源码位置（固定在上述提交）：

lib/src/services/im_sdk_relationship_reconcile_service.dart — resetForSession / _request / _runFriends / _runGroups

lib/src/services/im_sdk_relationship_directory.dart — reset / capture

已确认代码事实： resetForSession 重置阶段和目录；外层 _request 在等待后、完成和异常路径修改共享 phase 时没有捕获并验证最初 session generation。部分内部数据路径有 owner 校验，但外层阶段写入没有同等保护。

触发条件： 旧任务等待中切换账号或重建 session，新会话已开始 scheduled，旧任务随后完成或报错。

可能影响与边界： 旧任务可能把新阶段改为 completed/idle；新任务醒来后看到阶段不再 scheduled 而退出。这里确认的是控制状态隔离缺口，不等于已经证明跨账号消息或联系人数据泄漏。

建议修改方向： 每个请求捕获 session/job/reconnect generation，所有 phase 写入、释放 flight、错误回退都检查所有权。目录 capture 也应含代次或避免重复身份。

待执行验收： 用可控制的 Future 暂停旧会话校准；reset 后启动新会话；按各种顺序完成旧、新任务。旧任务不得改变新阶段，当前会话最终应有正确的完成信号。

A09 · iOS 关库链阻塞时，回前台无法恢复写入

优先级： 高。证据性质： 条件性共享等待风险。

源码位置（固定在上述提交）：

lib/src/services/sqflite_lifecycle_host.dart — handle / _closeDatabases / waitUntilWritesAllowed

lib/src/services/sqflite_lifecycle_guard.dart — closeDatabase

已确认代码事实： iOS pause 会等待多个 Store 的 closeIfOpen；resumed 在相同生命周期串行链后排队。waitUntilWritesAllowed 等待 close/open gate；Guard.closeDatabase 直接 await db.close，没有取消或总截止时间。

触发条件： 某个原生关库或其前置操作一直没有完成。没有真机证据证明当前用户已触发该条件。

可能影响与边界： 联系人、会话、消息、红包、资料等依赖写入许可的功能可同时等待。属于业务活性问题，不等于 UI 绘制线程必然被阻塞。

建议修改方向： 按 Store 记录关闭开始/结束/年龄、连接代次和当前生命周期。设计受控失败与句柄隔离恢复；不能 timeout 后直接复用或并发重开仍在关闭的同一连接。

待执行验收： 故障注入一个 close 永不完成、一个 close 晚完成，验证不会静默永久等待；旧句柄晚到不能覆盖新句柄；后台不能重新放开 SQLite 写入。

触发条件： 已允许并开启备份，满足前台、允许的首页 Tab、非聊天、空闲 3 分钟、Wi-Fi/以太网等限制；本次有大量新/变化项目或超限视频。

A13 · AI 停止回复后残留 streaming；旧错误可作用于新回复

优先级： 高。证据性质： 静态状态缺陷。

源码位置（固定在上述提交）：

lib/src/pages/ai_assistant/ai_assistant_page.dart — _stopAssistantReply / _sendComposer / _hasStreamingHistory / _beginAssistantReply

lib/src/api/ai_assistant_api.dart — uploadFile

已确认代码事实： delta 创建 status=streaming、time为空的消息；stop 保留 last.status，仅把 _replying=false。_sendComposer 还会检查任意 streaming 历史，因此继续拒绝发送。AI 异常分支只在旧 token 且 error.cancelled 时返回；旧 token 的非取消错误仍可修改当前最后一条回复。上传接口没有接收该流 token。

触发条件： 至少收到一个 delta 后点击停止；另一条路径是在上传阶段停止并发起新请求，旧上传随后非取消失败。

可能影响与边界： 前者可使当前 AI 页面持续提示 CHAT_BUSY；后者有覆盖新回复/提前清除 replying 的风险。没有声称已在真机复现。

建议修改方向： 引入明确 stopped/interrupted 状态，当前在途请求而不是任意历史状态决定可发送性；每个异步成功/错误路径都校验请求和账号所有权。停止上传与停止生成的后端语义要分别定义。

待执行验收： 首个 delta 后停止再发送；只存在旧 streaming 历史时恢复；上传停止后新请求开始，再注入旧非取消错误。新回复不得被旧结果覆盖。

待执行验收： 新账号授权相册但未启用备份：不得上传；已关闭状态不会被后续选择图片覆盖。检查正式安装包的实际 endpoint 与传输，故障切线不可降级到明文。

首页使用已访问 Tab 懒加载/保活，不是冷启动就初始化五个完整页面（home_page.dart、home_tab_stack.dart）。

在线状态已有行级更新与合并缓存，presence 快照有容量/账号数量限制（presence_provider.dart、coalesced_presence_cache.dart、contact_social_cache_store.dart）。

AI 文件加载器已有并发、队列和 24MiB 缓存预算，不能仅凭看见 Map 就断言无限内存泄漏（bounded_file_loader.dart）。

聊天已有消息窗口、懒构建、首屏 watchdog、回到底部取消/finally、图片档位和持久化优先级。问题应落到失效边界、单任务占用和所有权，不是把所有保护删除。

钱包已有请求合并、身份隔离、快照和超时，订单恢复也有限频；离屏刷新问题不等于没有任何节流或必然无限循环。

第一批：A01、A02、A03、A04、A06、A08、A13、A16 的控制流/协议边界测试与小范围修复。A17 的目的授权和明文传输单独高优先级整改，不等待帧率优化。
