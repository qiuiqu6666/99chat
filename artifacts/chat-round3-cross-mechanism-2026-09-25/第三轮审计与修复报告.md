第三轮找到了两个可复现的客户端交叉缺陷：同一失败因恢复副本维护而取得第二个重试身份，以及首个 SDK 草稿写入悬挂时后续编辑没有及时落入持久 head。两者都先补反例再修复。还修正了新已读水位重置旧任务冷却/预算的问题；补齐了 prepared 跨进程正向发送、旧 SQLite 模式升级和新旧重试身份的双适配器竞争测试。服务端已增加派发时复核、持久派发意图和 unknown 禁止自动重发，但服务端测试因缺失构建输入 **未执行**。

**当前不能宣布全链路验收完成。** 私聊/群聊视频仍会把 OSS 视频和缩略图设为 `PublicRead` 并把原始 CDN 对象 URL 写入原生消息；在线是否能匿名读取取决于账号/桶级阻止公开访问、策略和 CDN 配置，尚无带真实配置的匿名访问试验。双端腾讯 SDK、接收端唯一消息、真实成功后强杀对账、Web 全量构建和 Profile 性能也仍缺证明。此轮没有调整缓存、窗口或并发参数。

## 3A：重试资格、传输身份与恢复

### 已复现的版本冲突

原来同一个失败父操作使用 `state_version` 计算重试 operation/correlation。测试在第一条重试已进入 SDK 时，删除并重建父操作的合法恢复副本；触发器使父 `state_version` 增加，业务失败没有变化。修复前第二次点击生成了另一条重试身份，SDK 可以被再次调用。红测记录在 `retry-maintenance-before.jsonl`，绿测在 `retry-maintenance-after.jsonl`。

现在 `outbox_retry_identity.dart` 按父操作持久 `dispatchAttemptId` 计算稳定重试身份，`state_version` 只用于快照先后。没有持久派发尝试 ID 的旧失败不自动取得重试资格。`Im05Persistence._retryParentIsCurrent` 同时识别本轮稳定 ID 和旧版版本 ID，并仍要求父操作当前有明确失败、匹配恢复副本和一致的 payload。父操作成功补偿后，未派发子操作仍被拒绝。

仅更换 ID 不足以安全升级：旧版子记录可能仍在数据库里。`prepareOutbox` 现于同一个存储事务内查询同一父操作的其他子记录，发现后拒绝新子操作；SQLite、内存和 Web 三种事务实现均有此检查。内存反例证明旧子记录会挡住新版兄弟子记录；两套 SQLite 适配器对稳定 ID 与旧 ID 并发准备的测试证明只放行一个。已有旧子操作可按原 operation ID 恢复；父副本维护后的合法 prepared 子操作也能继续派发。父子链终态的安全回收尚未设计，所以此持久占位不能随意按时间清除。

重试测试直接读取传给 `MessageService.sendMessage` 的 `cloudCustomData` 参数：新 operation/correlation/指纹与子记录一致，`messageReply` 业务字段保留，旧父 operationId 被覆盖；子记录继续引用原加密 payload 与指纹。跨进程 fixture 还解密检查了 payload 中的回复字段和 @ 用户列表。这证明本地序列化与 SDK 调用参数，**不证明真实腾讯端接收的文字、附件或媒体内容**。

### prepared 正向恢复与 unknown

新场景 `prepared_resume` 在 Prepared 主记录、恢复副本和 draft acceptance 提交后强杀进程；新进程打开同一个 SQLite 文件，确认旧草稿不会再成为可发送编辑，用原 operation/correlation 获得派发资格，合成 SDK 返回成功后主记录进入确认态。随后重复恢复，SDK 调用总数仍为 1。`prepared-resume-final.txt` 与对应 `prepared-resume-*/write.jsonl`、`verify.jsonl` 是证据。这里恢复的是 `ImOutgoingSendCoordinator` 的 Prepared 派发路径；**没有**通过生产 `OutgoingOutboxRecoveryService` 的 SDK 消息重建/ServiceLocator 路径，也没有接收端。后两项仍需实测。

`dispatchIntent/sending/outcomeUnknown` 继续禁止盲重发；当前本地测试覆盖精确成功证据收敛、明显不可信的本地 optimistic/失败对象不算成功、成功补偿阻断子重试。真实 SDK 历史查询范围不足、查询失败、退群后的证据获取、长期 unknown 的 UI 解释尚未获得跨重启验收。未查到最近消息不等于远端未收到。

### 最后一秒已读与重试预算

`ConversationReadPolicy.conservativeTimestamp()` 对单聊可见时间 T 提交 T−1；同秒内未见消息不会被误清。若 T 是最后一个时间段且没有后续消息，此策略确实没有自动达到 T 的证据，不能靠等一秒、当前时间、T+1 或全会话清理补足。应区分“本地已可见到 T”和“SDK 已确认到 T−1”，并等待可证明 T 秒完整的 SDK/业务水位；锁定 SDK 若不能表达该边界，则需明确产品取舍。此项**未关闭**。

另外，W2 出错后合并新的 W3 曾把 `attemptCount`、`nextRetryAtMs`、`retryReason` 和 `createdAtMs` 重置；新消息持续到来可能无限刷新 15 分钟预算。现在合并新水位时继承旧任务的频控/阻塞信息，并保留 W1 回执不能覆盖 W2/W3 的条件删除。测试覆盖 blocked 后 W3 仍保留冷却。权限/存储阻塞在没有重连或新消息时如何被恢复触发，仍需独立机制；当前 `recoverPendingReadOutbox` 的显式重新激活只由重连路径调用。

## 3B：服务端执行授权与媒体访问

服务端原 `prepare()` 检查发送权限，但任务之后的 `deliver()` 不重新取得当前成员/发送/引用资格。现在首次执行、HTTP 重入和定时恢复均经同一 `deliver()`：它先核对目标会话、当前发送权限、视频所有者/类型/Ready/有效期、引用归属/会话/状态/有效期；媒体探测和组包后再次核对，并检查缩略图归属、父视频和类型。明确 4xx 拒绝标记失败；授权查询异常/5xx 暂缓、不默认放行。第二次复核通过后，带行锁的 `beginDispatch()` 才把 `pending` 持久转为 `unknown`，只有取得该唯一资格的执行者才继续公开对象并调用 IM。崩溃后 unknown 不由 `resumeDue()` 自动重发；该定时入口只取 pending。`markSent()` 不会把已撤销或过期引用复活为 confirmed。

该顺序降低了“准备成功后被移出群/禁言/撤销引用仍派发”的风险，也使两个 worker 的派发资格有一个持久顺序点，但**不能把权限撤销与远端 IM 调用组成原子事务**。第二次授权后到 IM 接受前仍有时间窗；已发出的请求无法由本地撤回。另一个升级边界是旧版本遗留的 `pending`：它可能是尚未调用 IM，也可能是旧版本在调用后崩溃而未记状态。不能仅凭锁超时自动认定未发，本轮未提供旧行迁移/隔离策略。

服务端单元测试新增准备后权限撤销、引用撤销、授权查询不可用、探测期间权限撤销、派发资格竞争、unknown 不重发、迟到成功不复活引用等场景，但 **Maven 在测试前失败**：`scripts/bootstrap/server-0.0.1-SNAPSHOT.jar` 缺失，见 `backend-tests.txt`。没有用跳过构建、陈旧类或伪造 JAR 制造通过结果。需要与当前源码相符、来源可追溯的 bootstrap 构建输入，之后还要跑真实数据库并发、服务端权限变化与双端接收测试。

媒体私密性仍是本轮最高的未关闭安全边界。`ChatNativeVideoService.deliver()` 调用 `oss.setPublicRead(videoKey/thumbKey)`；该方法实际调用 OSS 对象 `PublicRead` 且吞掉失败；`videoUrl(video, mediaBaseUrl)` / `thumbUrl` 写入的是原始对象 CDN URL，而不是另一个带业务授权的 HMAC 代理。阿里云官方文档说明对象 public-read 允许匿名读取且对象 ACL 优先于桶 ACL；账号/桶级 Block Public Access 可覆盖公开权限。CDN 默认 URL 可公开访问，URL 签名需要在节点单独配置。[OSS 对象 ACL](https://www.alibabacloud.com/help/en/oss/developer-reference/putobjectacl)、[Block Public Access](https://www.alibabacloud.com/help/en/oss/user-guide/block-public-access)、[CDN URL 鉴权](https://www.alibabacloud.com/help/en/cdn/user-guide/configure-url-signing)。因此源码证明“存在公开访问路径的配置风险”，**没有证明当前线上匿名访问成功**。上线前必须用无登录/无 Cookie 客户端分别验证 OSS 原站、CDN 冷/热缓存、缩略图/封面/转码、引用撤销后的旧 URL；同时实测腾讯原生视频发送时拉取还是接收后播放时拉取、历史消息续播。不能直接把历史消息写成短期签名 URL 就宣告修复。

## 3C：升级、草稿与长运行

旧库测试用同一 SQLite 文件先写入旧失败、Prepared、OutcomeUnknown 和已成功但没有恢复副本的记录，然后移除本轮新增的三列与触发器，再重新打开。第一次恢复能解释状态：无派发尝试 ID 的旧失败不误开放重试，Prepared 可继续恢复，Unknown 要求查询，已成功记录不因缺副本退回失败。再构造“父关联列已加、版本列及触发器尚未完成”的部分迁移形态，第二次打开仍可解释同一批操作。该测试覆盖**这些旧 outbox 状态和列/触发器的重复启动**，尚未覆盖旧草稿、缺失附件、媒体文件及升级同时崩溃的所有位置。

草稿红测证明首个 SDK `setConversationDraft` 永不返回时，同会话后续编辑 B 不能越过它调用第二个 SDK 写入，这是正确的顺序保护；但 B 原来也无法写入持久 head，重启会看到 A。现在 `_write()` 立即把当前编辑加密写入 head，SDK 写入仍走原会话/账号代次串行队列；事务内部再次核验当前编辑，防止慢加密或排队后旧 A 覆盖 B。测试在首个 SDK 调用保持挂起时，从另一个 `ConversationDraftService` 实例读出 B，且 SDK 调用数仍为 1；释放首调用后 B 才顺序同步。**SDK 调用真的永久挂起时，同会话 SDK 队列仍不会自动恢复**，需要经过验证的 SDK 生命周期/取消协议，不可简单起第二队列。其他会话/账号代次有独立队列，但仍需真实登录切换验证。

持久 draft head 当前只保存 `protected_text` 与身份；未提交回复目标和 @ 用户身份/出现位置仍没有结构化恢复。Prepared payload 里有这些字段，不等于未发送编辑重启后能恢复。应另建带版本的草稿结构，并处理回复目标撤回、成员离群及编辑变化。`message_draft_acceptance` 与父子重试记录目前缺安全回收规则；过早删除会让迟到 SDK 草稿或旧子操作失去拒绝依据，永久保留也不适合作为最终策略。回收必须先证明没有当前 head、未完成父子操作、迟到写入或历史证据引用，再单独压缩 payload 与身份/接纳锚点。

已有 SQLite COMMIT 延迟外键失败测试证明失败事务不发布结果，重开保留已提交状态且不自动重放 action；本轮没有扩展到 `SQLITE_BUSY`、磁盘满、IO 错误和旧回调竞争。SQLite 文档说明 COMMIT 返回 `SQLITE_BUSY` 时事务可能仍活跃、可稍后重试，其他错误可能回滚一个语句或整个事务，不能把所有提交失败一概解释为回滚。[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)。
