## 2. 当前链路及其正确性边界

| 阶段 | 当前主要入口／职责 | 需要保持的事实 |
|---|---|---|
| 打开会话 | `app_chat_route.dart`：会话规范化、已有路由复用、预热前预占 | 同一 Navigator／账号 generation／会话／模式共享首次打开；Future 在真实路由退出后完成 |
| 首屏与历史 | Chat 与既有 viewport／history 协调逻辑 | 保持首屏连续；历史按需上拉；首屏显示计时与后台工作区分 |
| 页面覆盖与返回 | `_performChatHistoryAfterOverlayReturn`、既有阅读锚点维护 | 已有可见窗口时保持阅读位置，不无条件重建最新窗口或跳底 |
| 编辑 | `ConversationDraftService`、`ChatDraftController` | 编辑身份属于账号、会话和具体一次编辑；A 的迟到任务不能覆盖 B |
| 提交 | 输入框捕获提交 ticket → `ImDraftSubmissionContext` → send coordinator | 接纳前不把清空输入解释为持久保存；同文 B 仍是独立编辑 |
| 本地接纳 | `prepareOutbox`：主记录、恢复副本、draft acceptance | 三者成功提交后，才发布接纳并清理属于 A 的草稿 |
| 派发 | `recordDispatchIntent`＋lease／fence＋条件写入 | 同一操作同一尝试仅一个执行者获得 SDK 调用资格 |
| 结果仲裁 | SDK 回调／history／realtime → `Im05Persistence` | 结果未知不盲重发；较弱迟到失败不能覆盖已确认成功 |
| 持久化与投影 | 存储事务真实提交 → 不可变结果快照 → UIKit 行与会话预览 | COMMIT 失败不能通知成功；已显示的失败也要主动收敛 |
| 重试 | 当前 UI 提示 → 持久父操作／版本 → 新重试身份 → 最终 CAS | 按钮展示时的 canRetry 不是派发授权；补偿成功后旧按钮不能再发 |
| 已读 | 页面观察水位 → durable read outbox → SDK 清理 → 条件确认 | W1 的完成不能抹掉 W2；未知水位不能变成 0 或全局清理 |
| 重启 | SQLite 状态／编辑归属 → prepared 恢复或 unknown 核对 | 不依赖旧 ResultView、内存 alias 或先前消息对象存活 |

对应源码：[路由][route]、[Chat 返回入口][chat-return]、[草稿服务][draft]、[发送协调器][send]、[Outbox 持久化][persistence]、[已读队列][read-outbox]。

## 3. 2A：第一轮边界的反例、修复与证据

### A1. 查询失败与没有记录必须分开

最短风险序列：成功已形成 → Outbox 读失败 → 把异常当 null → 旧失败回调覆盖成功／开放重试。

`readOutboxResult` 现在分别表达：主副本都没有、只有恢复副本、非终态缺副本、终态副本已回收、身份冲突、存储不可用。`unavailable` 带不含正文的错误类型原因。终态主记录仍能解释成功；非终态缺材料只进入暂缓。`ChatFailedMessageRetryService` 不再因无法定位、身份不明或读失败进入定时降级重试。

`canRetry` 除主状态外，还要求可信快照、已记录结果的恢复副本、对应的 attempt 一致。不能仅看到 failed 就授权重试。

已验证：存储错误返回 unavailable、canRetry=false；已知成功不会被弱失败裁决降级。已有失败行在读故障期间可能保留原显示，但点击后仍要经过持久仲裁，不把该显示当作发送权限。**没有把“未找到 Outbox”证明为“确定旧版本消息”，因此当前采取保守阻断。** 需要兼容的旧失败消息应另行建立可证明的迁移／人工处理规则。

证据：[边界测试][outbox-tests]、[结果仲裁回归][arbitration-tests]、[最终日志][final-tests]。

### A2. recoveryRevision 不再充当长期主状态版本

风险序列：副本 revision=18 → 副本回收／重建为 1 → 消费者对新旧状态失去可靠比较。

新增主记录 `state_version`。迁移起点取至少 1，并吸收已有 recovery revision；主记录变更及副本插入、更新、删除都推进主版本。版本允许跳号，要求严格单调，不要求一次业务动作只加一。副本清理不会删除承担终态解释责任的主记录。

SQLite 用触发器覆盖底层写入；内存与 Web 适配器同步维护逻辑。ResultView 只接纳严格更新的完整快照。同版本不允许再次解释为另一状态。

已验证：多条已提交状态路径版本增长；两个存储适配实例交替写入时视图仍更新；终态副本清理后可重新读取成功。**这不是独立多进程 SQLite writer 竞争的完整证明。** 主记录及 acceptance ledger 的长期保留／回收策略也尚未完成，不能声称已经实现最小化存储。

源码：[迁移与触发器][schema]、[存储提交观察][ingress]、[状态裁决][persistence]。

### A3. SQL 执行成功与事务提交成功是两个边界

这里复现了两类实际缺口。

1. 恢复副本条件 UPDATE 返回 0 行时，主记录可能已经更新。仅判断 SQL 没有抛错会形成主副本不同步。现在关键耦合操作遇到 0 行写入抛错，整体回滚；包括派发意图、unknown、人工关闭、投影完成等路径。
2. 通过 SQLite 延迟外键构造最终 COMMIT 失败，事务回调已经返回，但原生连接仍可能停留在失败事务。现在 `MessageCoreStore.runTransaction` 在这类提交阶段异常后清空并关闭连接，后续重新打开；不自动重放用户 action。

快照在事务内部收集，但**只在实际事务 Future 成功返回后发布**。回调返回不等于发布时机。COMMIT 故障测试核对主记录、副本、通知次数及重新打开后的读取，避免“UI 成功、磁盘没提交”。SQLite 官方也明确说明延迟外键检查失败时 COMMIT 失败且事务仍保持开启。[SQLite 外键事务说明](https://www.sqlite.org/foreignkeys.html)

证据：[修复前零行更新反例][cas-before]、[COMMIT 故障测试][outbox-tests]、[数据库事务入口][core-store]。本轮没有覆盖所有 SQLITE_BUSY／磁盘满／设备文件系统故障组合，不能把一种提交失败扩大为所有数据库异常已验收。

### A4. 数据库正确后，已经显示的失败行必须自己刷新

真实 Widget 探针复现：失败行已显示 → provider 成功已提交 → error 图标仍在。原因除了需要主动通知，还包括 `send_adoption` 事件 ID 对失败与后续成功相同，后一个状态被去重层吞掉。

修复包括：

- 活跃结果视图通过提交后的通知触发 UIKit 投影；读取一次冻结快照，再应用状态、版本与重试资格。
- 行更新事件纳入持久 stateVersion，避免不同规范状态共用一次去重身份。
- 同步修正会话预览；该路径不再次调用发送完成业务回调、不再次清草稿。
- 终态、会话窗口移除、账号清理时解除相关订阅；weak reference 只负责注册表保留策略，不能代替持久化或活跃订阅。

已验证：真实 UIKit 消息行先显示失败图标，成功补偿后无需用户点击／新消息即移除错误；全局模型的预览状态更新，重试资格关闭。**完整会话列表 Widget 的视觉端到端测试尚未完成。** 页面覆盖不等于窗口删除；订阅的生命周期跟随保留窗口与账号，不能解释成每次离开页面都立即取消。

证据：[修复前 Widget 探针][widget-before]、[真实消息行测试][widget-tests]、[UIKit 活跃订阅][global-model]。

### A5. 检查一次 canDispatch，不足以保证并发只发一次

同一 prepared 操作的两个协调器同时发起，最终通过事务中的 lease／fence／条件状态写入竞争 `dispatchIntent`。测试拦截的是 `MessageService.sendMessage` 实际调用，两个请求共计一次调用；调用抛错后仍进入 unknown，后续恢复不会再调 SDK。

继续追查旧重试按钮后，补上了此前主要依赖内存状态的入口：

- 点击后按 SDK local ID 找到原 durable failure，读取最新完整裁决。
- 重试记录保存 `retry_of_operation_id`、`retry_of_state_version`。
- 相同父操作版本得到同一个确定性重试 operation／correlation，两个点击不能各造一个可派发操作。
- prepared 写入、恢复评估、最终 dispatchIntent 都检查父操作仍是该失败版本。
- 重用原加密 payload、指纹、暂存附件引用，避免本地重新创建消息导致 payload 身份漂移。
- 获得持久派发资格后，才替换旧 UI 行；被拒绝时不先删除原消息行。

已验证：并发重试实际 SDK 调用=1、UI admission=1；重试 prepared 后插入成功补偿，再进行最终派发，SDK 调用=0、UI replacement=0；新的恢复评估也拒绝这个过期重试。

这个保证的线性化边界是成功提交的 dispatchIntent。**请求已经离开客户端后，后来的补偿或取消不能证明远端未执行。** 这里没有宣称腾讯服务端 exactly-once；真实接收端重复消息仍需双端对账。

证据：[派发与重试竞争测试][dispatch-tests]、[持久父版本检查][parent-guard]。

### A6. provider 证据既要匹配身份，也要有来源和成功状态

补偿入口要求 owner／会话／operation／correlation／payload 指纹一致，msgID 非空，且 SDK 对象状态为 SEND_SUCC。新增明确来源：SDK history、SDK realtime、应用投影；应用乐观投影即使填了成功状态也被拒绝。

已验证：身份完全匹配的 SENDING、SEND_FAIL 和 appProjection 不会升级成功。来源枚举是代码调用约束，**不是证据的加密签名或对 native SDK 契约的替代**。上游标错来源仍是需要代码审查防止的问题。

operation／correlation 必须来自可跨重启读取的字段。现有发送身份写入 cloudCustomData；不能用 localCustomData 的本地保留能力推断云端也能取回。此次重启测试重建了消息对象，但 provider 消息来自序列化 fixture。因此“真实腾讯历史／实时消息在重启后仍返回完全一致字段”仍未验收。

### A7. 草稿等待超时不再释放底层写队列

已有队列继续等待真正的 SDK Future 完成；外层调用方 timeout 不让后继 B 越过未完成 A。编辑先保存到加密 head，写 SDK 前后检查当前编辑身份。accepted 的旧 A 即使迟到，也不能覆盖同文新 B；检测依据 acceptance ledger，不能只比较当前 head 或文字。

已验证：调用方超时后底层 A 仍未结束时 B 不启动；A 结束后按队列顺序收敛；已接纳 A 的迟到写入不会覆盖新 B。Dart 的 timeout 不取消原始 Future，因此只在返回后检查令牌不足以撤销底层写入。[Dart Future.timeout](https://api.dart.dev/dart-async/Future/timeout.html)

**剩余限制：原生 SDK 如果永久不返回，当前该队列可能持续阻塞。** durable head 能保存业务编辑，重启可优先恢复；本轮没有提供已经验证的原生取消／连接重建协议，也没有用另一个 timeout 假装取消 SDK。这个活性边界必须留在 2D，不应宣称草稿链路完全关闭。

## 4. 2B：F4／F5／F6 的具体行为

### F4：普通返回保留阅读窗口

`_performChatHistoryAfterOverlayReturn` 恢复 registry 后，如果已有可见历史就直接保留窗口，去掉无条件跳到最新位置的分支。空窗口仍走原来的恢复路径。

现有阅读锚点测试、C2C 历史锚点契约、媒体路由生命周期测试均在最终回归中通过。本轮没有重做锚点算法，也没有把这些底层测试等同于完整页面的“锚点撤回＋图片布局变化＋用户主动滚动”验收。该组合需要保留：按消息身份与相对偏移恢复、失效时选择邻近锚点、用户滚动后旧恢复任务失效。

### F5：首次打开的预占覆盖预热等待期

预占在第一个 await 前登记；key 包含 Navigator、owner、generation、规范化会话与路由模式。预热失败／超时有边界地继续开页；账号已变或全部发起 context 销毁则取消。一个调用方销毁不会取消其他仍挂载的调用方需要的路由。

共享调用等待同一个真实路由退出；清理检查 pending 对象身份，旧任务不能删除更新的预占。既有路由复用和搜索锚点路由保持各自契约。

新增路由／已读边界文件中 8 个有效用例通过，包括预热成功、失败、超时、账号失效、调用方销毁组合，以及水位／队列竞争。这里使用真实 Navigator，但 route factory 是受控测试页，并非启动完整聊天页和原生 SDK。

### F6：已读不越界，失败按原因恢复

本轮没有补“最多 10 次”这样的统一次数阈值。

| 情况 | 当前规则 |
|---|---|
| c2c 同秒 M1 已见、M2 未见 | 清理水位采用 T−1；T 秒的消息保守保留，避免误读 M2 |
| group | 使用有效 sequence；不把 timestamp 混作 sequence |
| 水位未知／无效会话 ID | 暂缓，禁止默认 0；禁止空字符串或意外类型级清理 |
| 显式全会话清理 | 单独显式授权参数；普通生命周期 markRead 不能默默走全清 |
| 可恢复临时错误 | 在有限的 15 分钟任务预算内退避；这是本轮保护边界，不是实测最佳参数 |
| 参数／权限／存储类错误 | blocked，退出定时重试；新目标或对应恢复处理才继续 |
| 需连接恢复／未分类错误 | 退出定时重试，真实 SDK 重连后恢复符合条件的任务 |
| SDK 频控 -10113 | 先保留频控阻塞时间，再走分类退出；修复过一次实际回归失败 |
| W1 发出、W2 入队、W1 返回 | acknowledge／markRetry 只作用于 W1 捕获的版本，保留 W2 |
| 多次入队落在同一毫秒 | 单独保存 read_event_at，结算版本单调推进，W1／W2／W3 不互相擦除 |
| 重复同一目标／批量占位 | 保持已有退避和精确水位；占位不能覆盖已有更强目标 |

T−1 有明确产品代价：最后一秒的已看消息可能仍计入 SDK 未读，直到后续有可表达的更大边界。不能将它宣传为“逐条精确已读”。秒级包含边界与 0 的含义需继续对照锁定 SDK 8.9.7545 真机实测；当前实现和测试选择保守边界。

证据：[路由与水位竞争测试][route-tests]、[已读策略][read-policy]、[已读队列][read-outbox]、[最终回归][final-tests]。SDK 接口参考：[腾讯 Flutter 会话未读](https://cloud.tencent.com/document/product/269/75374)。

## 5. 2C：接纳点、草稿归属和强杀对账

当前顺序为：捕获本次编辑和完整发送 message → 持久化可恢复加密 payload → prepared 主副本与 draft acceptance 同一事务提交 → 通知本次提交接纳 → 仅清理对应编辑 → 条件记录 dispatchIntent → SDK。

新增持久信息：

| 存储 | 用途 |
|---|---|
| `message_draft_head` | 按 owner／conversation 保存 draftId、加密文字、accepted operation |
| `message_draft_acceptance` | 按 owner／conversation／draftId 记录已经被哪个操作接纳；抵御迟到 A 覆盖 B |
| Outbox `state_version` | 终态与重试解释的长期版本 |
| Outbox `retry_of_*` | 重试所依赖的父失败操作及版本 |

两个文本都为“same”的连续编辑有不同 draftId。A 接纳不能清 B；一个 draftId 不能被两个 operation 接纳，第二次尝试整体回滚，不能留下第二套半成品 Outbox。

prepared payload 保留消息类型、回复／@ 所需消息数据与附件引用；清 reply target 也要等接纳且目标仍属于本次提交。**尚未提交时的草稿 head 仍只持久化文字，不能恢复完整 reply／@ 编辑状态。** SDK 自身文本草稿也不能承担完整结构化编辑语义。[腾讯 Flutter 草稿说明](https://cloud.tencent.com/document/product/269/75382)

### 四个强杀断点

执行方法：子进程使用真实 SQLite 与加密 payload；写入带场景和 nonce 的 ready 文件；父进程只对核实后的本次子进程 PID 发出强杀；再启动新的 Flutter test 进程打开同一数据库。writer 被强杀产生非零退出属于预期；verify 必须成功。

| 强杀位置 | 新进程读取结果 | 验收含义 |
|---|---|---|
| 接纳事务尚未提交 | draft=A；无 durable Outbox 接纳 | 不虚报已经可靠接纳，已持久编辑可恢复 |
| prepared 已提交、SDK 草稿未清 | 同一 prepared 操作；draft 不恢复为可重发 A | acceptance ledger 能解释跨存储的清理归属 |
| dispatchIntent 后结果未知 | durable state=dispatchIntent；canRetry=false；无恢复发送 | 请求可能发出，必须核对，不能自动再发 |
| SDK 成功、本地结果事务失败 | durable state=sending；canRetry=false；用重新反序列化证据修复 | 不依赖旧内存对象；无盲重发 |

## 7. 性能审查口径

本轮验证的是日志契约，尚未回答“具体慢多少、缓存或并发应调到多少”。

- `executionUs` 是阶段经过时间，包含 await 时就是等待与执行的合计，不能直接解释为主线程 CPU 时间。
- 一个共享 producer 的资源成本记一次；每个 caller 的等待、超时仍分别保留。调用方 timeout 不结束 producer span。
- 不包含 `messages_first_visible` 的 trace 必须保留，并区分空会话、取消、复用、账号失效、失败／超时；这也是后续分析器的验收要求，不能只筛成功样本计算分位数。
- 关闭开关时 `measure` 直接执行 action、`queueSpan` 返回 null，不创建 span／计时器。已检查的诊断读取原本就在业务路径中，不能把开关外已有读取误称为开启日志新增读取。
- 不把并行阶段耗时相加；应沿同一 trace 找实际阻塞首屏的依赖路径。
- 稳定用户 ID 的普通摘要不是匿名化保证，也不能用于业务授权。日志脱敏与业务身份校验是不同职责。
